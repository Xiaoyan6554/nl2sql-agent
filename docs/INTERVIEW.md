# 面试讲解与追问

讲解稿以实际代码和结果为依据。人工错误分类未完成前，不要声称自己已经分析过具体错误原因。
请亲自复跑并能逐行解释核心模块，再将第一人称稿用于面试。

## 一分钟版

我做了一个自然语言查询 SQLite 的个人项目，用 Spider 公开数据集做固定子集评测。
我先用整库 schema 一次生成 SQL 建立基线，再加入选表选列、校验修复和训练集示例检索。
这次四个版本的正确题数依次是 111/150 → 114/150 → 115/150 → 120/150，原始结果和代码版本都保留在仓库里。

项目重点是能解释改进是否有效。真实评测没有触发修复，所以我不会把 v2 的差异说成重试带来的提升。
检索版本次更好，但消耗更多 token，单次实验也不能证明稳定收益。
执行端使用 SQL AST、只读连接、SQLite 操作白名单和资源上限。
我还做了安全回归，结果是 28/30 拒绝、2 条限量处理。

## 五分钟版

1. **问题与边界。** 目标是把自然语言转为可执行且含义正确的 SQL。只支持 SQLite 和本机演示；
   不把它包装成公司系统，也不引入向量数据库、微调或复杂部署。
2. **建立参照。** 看 baseline.py：一次模型调用，整库 schema，直接 SQL 输出。
   看 run_eval.py：先 gold 预检，再逐题执行与比较，记录成功率、延迟、调用和 token。
3. **逐项改进。** schema_link.py 返回表列 JSON，代码核验对象并保留键；无效输出回退完整 schema。
   graph.py 用条件边连接校验、执行和修复，最多两轮。合法空结果不会被强行改成有结果。
4. **检索与防泄漏。** retrieval.py 使用 BM25，只索引 train_spider，排除所有 dev 数据库。
   每个问题检索训练示例，trace 保存命中的 ID。没有将 gold SQL 放进生成提示。
5. **实际结果与反例。** 打开 docs/RESULTS.md，逐项展示结果。当前没有观测到 repair 的真实纠错案例，
   只能说分支通过测试。检索版本次最好，不对单次差异做因果或显著性结论。
6. **安全和局限。** 拦截不依赖模型服从提示。只读、白名单、时限和结果上限共同保护执行。
   词法异常由真实攻击探测发现并修复。人工分类、官方 test-suite、多次重复实验是下一步。

## 二十个追问

### 1. 为什么先做基线？
没有基线无法知道额外模块是否值得。baseline.py 刻意限制为一次调用，整个 schema 保持可见。
对比必须使用同一题目清单和指标，不能只挑改进后答对的题。

### 2. 为什么用 LangGraph？
graph.py 将状态、节点和条件分支分离，重试次数和终止条件可测试。
当前没有复杂多 Agent 协作，也不需要引入持久化检查点服务。

### 3. Schema Linking 是什么？
让模型选择相关表和列，减少生成提示中的无关结构；程序保留主外键。
它会多消耗一次调用，也可能误删所需结构；不能预设它一定更好。

### 4. 为什么不用简单正则判断 SQL 安全？
正则无法可靠区分字符串中的关键字、多语句、嵌套查询等。
safety.py 解析 SQLite AST，再由 db.py 的 authorizer 执行第二层白名单检查。

### 5. 只允许 SELECT 是否能确保安全？
不能。SELECT 仍可能访问系统表、调用扩展或文件函数、生成巨大结果、执行昂贵 JOIN。
因此还需要对象和函数白名单、只读连接、执行时限和结果上限。

### 6. 如何判断表和字段存在？
validate.py 在受限只读连接上执行 EXPLAIN QUERY PLAN，交给 SQLite 编译器处理别名、CTE 和相关子查询。
这里不执行查询来“猜”对象是否有效。

### 7. 为什么 repair 最多两轮？
这是明确的调用和延迟上限，避免无限循环。当前上限来自工程取舍，不是假称通过实验选出最优值。
测试会故意连续返回错误 SQL，检查两轮后一定终止。

### 8. 为什么不修复空结果？
空结果可以是正确答案；自动追求非空可能改变筛选条件。
当前只把显式校验或执行错误反馈给模型，结果含义错误留给评测和人工分析。

### 9. 为什么修复时恢复完整 schema？
前面的选表选列可能漏掉关键表，继续给相同裁剪 schema 可能反复失败。
repair.py 因此带上完整结构，但也会增加 token。

### 10. 执行准确率怎么算？
本次 baseline 为 111/150，检索版为 120/150。
无顶层 ORDER BY 按多重集合比较，保留重复行；有 ORDER BY 按顺序比较。列顺序保留，不做模糊匹配。

### 11. 为什么不直接比较 SQL 字符串？
不同 SQL 可以在当前数据库上返回相同结果，字符串比较会误判。
但单数据库结果相同也不证明语义普遍等价，所以还可以接入官方 test-suite。

### 12. LIMIT 会不会影响准确率？
会。因此展示接口添加 LIMIT，评测使用完整结果。
超过资源上限时明确失败，不对截断的预测与 gold 做相等比较。

### 13. 如何防止示例检索泄漏？
只读 train_spider，并过滤全部 dev 数据库，不只过滤当前抽中的题。
测试同时检查过滤逻辑与真实索引；trace 保存训练示例 ID 便于追溯。

### 14. 为什么先用 BM25？
它依赖少、原理可解释、可在本地快速检索。当前只按英文词元匹配，不具有向量语义召回能力；纯中文问题可能没有示例命中。
检索返回的句式相似并不保证 SQL 结构适用。

### 15. 哪个改进没有被证明有效？
当前 repair 在完整真实评测中没有触发，因此没有真实纠错收益证据。
v1/v2 分数差可能包含生成波动，不能宣称修复带来这部分提升。

### 16. 为什么 temperature=0 还可能不一致？
远端模型别名、基础设施和解码实现不一定完全确定。
仓库记录请求名与返回名、日期、温度、代码提交、数据哈希；无法替供应商固定权重。

### 17. 出现网络错误时如何统计调用和 token？
llm.py 先记录一次尝试，关闭隐式 SDK 重试，失败也计入调用次数。
没有返回 token 就记 None，同时保留已报告部分，不能当作免费或零用量。

### 18. 安全测试证明了什么？
本批 SQL 用例 28/30 拒绝，2 条被限量，另有 6 条真实提示探测。
它证明这些用例符合预期，不证明所有输入安全；尤其 VM 超时不是进程级沙箱。

### 19. 遇到过什么真实问题？
官方下载配额超限后换为固定公开镜像并核验摘要；SQLite 文本含非法 UTF-8，改为保留字节差异；
模型拒绝文本触发 TokenError，补上安全拒绝和回归测试。这些都在 NOTES.md 中有记录。

### 20. 下一步最值得做什么？
先本人复核导出的失败题，填写 ERROR_ANALYSIS.md；再进行重复实验和官方 test-suite 验证。
根据真实错误分布决定改进方向，避免只凭感觉堆功能。暂时不填未经本人确认的分类结论。
